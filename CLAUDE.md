# Ki Sapato — guia para o Claude

E-commerce de calçados. Idioma: português (pt-BR). Monorepo npm workspaces.

## Estrutura
- `apps/web` — Next.js (App Router) com o layout do protótipo; consome a API. Sessão e sacola no navegador (`src/lib/session.tsx`, `src/lib/cart.tsx`).
- `apps/api` — Express + TypeScript + Prisma (PostgreSQL). Módulos em `src/modules/<nome>`: auth (JWT + bcrypt), products, categories, home, orders (checkout demonstrativo), admin (CRUD), uploads (fotos em disco).
- Banco: PostgreSQL hospedado na Discloud. Migrations em `apps/api/prisma/migrations`.

## Conta do cliente (módulos `auth` e `account` da API; `/auth` e `/conta/*` no web)
- Cadastro com nome completo, CPF (validado, só dígitos, único), e-mail, **celular obrigatório** e senha forte (8+ com letra maiúscula, letra minúscula, número e caractere especial; regras em `src/lib/validation.ts` e `web/src/lib/validators.ts`, mantenha as duas iguais).
- Cadastro em 2 etapas: `POST /auth/register` cria a conta como `pendingVerification` e envia um código de 6 dígitos por e-mail e, se a confirmação do telefone estiver ligada, outro por SMS (sem sessão); `POST /auth/register/verify` confere os códigos juntos (só consome se todos estiverem certos) e abre a sessão. `PHONE_VERIFICATION` (`auto` | `required` | `off`, padrão `auto`) decide se o SMS é exigido: `auto` liga só quando há provedor de SMS, então sem provedor o cadastro pede só o e-mail (o telefone continua obrigatório, mas fica não confirmado: `verifiedPhone` nulo e sem recuperação por SMS) e passa a exigir o SMS sozinho quando o provedor for configurado; `POST /auth/register/resend` reenvia (1 min de intervalo). Login de conta pendente responde 403 `VERIFICATION_REQUIRED`. Conta pendente não reserva e-mail/CPF (um cadastro novo a substitui) e não recupera senha. Sem e-mail configurado (ou com `PHONE_VERIFICATION=required` sem SMS) o cadastro responde 503 (`capabilities.registration=false`). Contas antigas (anteriores à confirmação) seguem entrando normalmente.
- Sessão: JWT com `tv` (= `Profile.tokenVersion`); `requireAuth` consulta o banco, então trocar a senha ou o 2FA derruba as outras sessões. `passwordHash` e `twoFactorSecret` ficam fora das consultas por padrão (`omit` em `src/lib/prisma.ts`).
- 2FA opcional por aplicativo autenticador (TOTP), segredo cifrado com `DATA_ENCRYPTION_KEY`, 10 códigos de emergência (hash). O login com 2FA devolve `{ twoFactorRequired, challenge }`; o painel admin (`AdminLogin`) também trata esse passo.
- Recuperar senha por e-mail ou telefone confirmado: código de 6 dígitos, hash, 15 min, 5 tentativas. E-mail: `GMAIL_USER` + `GMAIL_APP_PASSWORD` (atalho do Gmail, senha de app) ou `SMTP_URL` (qualquer provedor, tem prioridade); teste com `npm run mail:test -w @ki-sapato/api -- destino@exemplo.com`; SMS usa o driver `twilio` (`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`) ou `console` (só fora de produção). Trocar de provedor = novo driver em `src/lib/notify.ts`.
- Endereços: vários por conta, exatamente um padrão (regra mantida nas rotas). O checkout usa `addressId` e exige CPF na conta (`CPF_REQUIRED`).
- Cartões: só token do gateway + bandeira + 4 últimos dígitos + validade; nunca número nem CVV. Fica desligado até haver gateway (`CARD_PROVIDER`).
- Limites de tentativas em `src/middlewares/rate-limit.ts` (memória do processo; `trust proxy` = 1 em produção).
- Testes: `npm test -w @ki-sapato/api` (regras de segurança, sem banco).

## ERP (módulo `erp` da API; botão "Atualizar do ERP" em Produtos no painel)
- Só leitura (SOAP Macle ControleWS, `ERP_URL`). No máximo 4 chamadas ao ERP ao mesmo tempo (`client.ts`): com 8+ o serviço devolve listas VAZIAS sem erro. `POST /admin/products/erp-refresh` começa em segundo plano e responde 202 com o andamento (repetir só devolve o andamento); `GET` do mesmo endereço dá etapa, % e o resultado da última rodada (memória da API). A tela (`lib/erp-refresh.tsx`, no painel todo) consulta a cada 1,5 s, mostra a janela de andamento/resultado em Produtos e um aviso de conclusão nas outras telas. O banco fica longe (~170 ms por ida e volta): `applyPlan` grava só o que mudou e marcas/categorias ficam em cache na rodada (`catalog.ts`). A rodada (`erp/sync.ts`) lê os itens marcados para o site de todas as marcas (`getDadosItem`), junta com os produtos já importados e grava pelo `applyPlan` (preço, cores, numerações e estoque). Produto novo nasce DESATIVADO (foto, descrição, selo e "ativo" são do site). Marca, classe e categoria que faltarem no site são criadas na hora (`erp/catalog.ts`; marca com o nome do ERP em título, vinculada pelo `erpCode`; tipo do ERP → categoria pelo de-para `CATEGORY_BY_TYPE` em `erp/mapping.ts`, tipo fora da tabela vira categoria com o próprio nome; classe pelo tipo, depois pelo grupo) e o resumo do painel lista o que foi criado. O que foge das regras vira pendência na tabela `erp_issues` (chave marca + referência; `productId` quando o produto já existe): não importado (grade mista, gênero desconhecido, sem preço, sem referência, erro ao gravar) ou importado com ressalva (`needsAttention` em `erp/sync.ts`: ERP desativou o item, tipo/gênero/nome diferente entre cores, estoque fora da grade). Cada atualização regrava as pendências e apaga as resolvidas. `GET /admin/products/erp-issues` alimenta o aviso "Há X produtos que precisam da sua atenção" em Produtos, que filtra a lista e mostra um ícone com o motivo ao passar o mouse. Uma atualização por vez (409 se já houver).
- Cada cor é um item do ERP: só entram as cores marcadas; ao marcar outra cor, a próxima atualização a acrescenta ao produto. Cada cor tem `active` (à venda) e `erpFlagged` (o ERP marca o item para o site). Cor que o ERP deixa de marcar (`classeItemSite` = NONE) fica DESABILITADA e não pode ser habilitada no painel; cor marcada pode ser desligada só no site (chave À venda/Desabilitada no formulário do produto; a atualização não a religa, a não ser que o ERP desmarque e marque de novo). Desabilitada (`ProductColor.active = false`): some da loja (`colorsOf`) e as numerações dela ficam com estoque 0 (o saldo real do ERP segue no plano); marcando de novo, ela volta. O resultado da atualização lista as cores desabilitadas/habilitadas e o admin mostra a etiqueta "Desabilitada no ERP". Produto sem nenhuma cor marcada fica sem cores na loja, mantendo o preço.
- Também há o script `npm run erp:import -w @ki-sapato/api -- --ref <referência> [--apply]` para um produto só.

## Medição do site (módulo `analytics` da API; `lib/track.ts` e `components/Track*.tsx` no web; documentação em `docs/analytics/`)
- Fluxo: SDK do site (`track()`, lote com `sendBeacon`) → `POST /api/events` (sempre 204; buffer em memória, grava em lote a cada 5 s) → `analytics.events` (particionada por mês, esquema interno) → resumos diários (`analytics.refresh_daily`, a cada 15 min e às 3 h) → views `bi.v1_*` (contrato versionado, sem dado pessoal). A compra (`purchase`) e erros 5xx são gravados no servidor; o site manda `X-Ks-Aid`/`X-Ks-Sid` em toda chamada à API para ligar a compra à visita.
- Fonte única dos eventos: `modules/analytics/registry.ts`; das métricas abertas a BI/IA: `modules/analytics/metrics.ts`. Mudou evento, view ou métrica? Rode `npm run analytics:docs -w @ki-sapato/api` (banco com as migrações) e commite `docs/analytics`: um teste falha se a documentação ficar para trás.
- Leitura por IA/BI: API `GET /api/metrics/v1/*` (chave `METRICS_API_KEY`), servidor MCP (`npm run analytics:mcp`), SQL no esquema `bi` (usuário `bi_reader`). `run_sql` só aceita SELECT em `bi` (`sql-guard.ts`). Guia para agentes: `docs/analytics/AGENTS.md`.
- Privacidade: sem dado pessoal nos eventos, IP não guardado, respeita "Não rastrear"/GPC/`ks:optout`, nunca mede `/admin`; identificação do cliente logado desligada por padrão (`ANALYTICS_IDENTIFY`). Datas vão ao banco como ISO com "Z" (data "pelada" deslocava 3 h).
- A API sobe sem erro mesmo se as migrações da medição não estiverem aplicadas (fica desligada e avisa no log).

## Comandos
- `npm run dev` (api + web), `npm run typecheck`, `npm run lint`, `npm test -w @ki-sapato/api`.
- `npm run db:migrate` (dev), `npm run db:deploy` (produção), `npm run db:seed`.
- Banco local para testar sem tocar na produção: o `.env` aponta para o banco compartilhado (que é produção); para testes, exporte `DATABASE_URL` e `DIRECT_URL` para um Postgres local descartável antes de rodar migrate/seed/API.

## Regras
- Nunca digitar senhas/segredos em `.env`: o usuário preenche. `.env` não é versionado.
- Admin inicial vem do seed com `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`.
- Fotos de produtos ficam em `UPLOAD_DIR` (servidas em `/uploads`); em produção use um diretório persistente e faça backup junto do `pg_dump`.
- Deploy: dois apps na Discloud, `apps/api/discloud.config` (`kisapato-api`) e `apps/web/discloud.config` (`kisapato`). O web precisa de `NEXT_PUBLIC_API_URL` na hora do build.
- Git: push só na branch `pre-prod`, com mensagem de commit completa. Sem commit/push sem o usuário pedir.
- O front gerado no Lovable (TanStack Start + Supabase) foi abandonado; está no histórico (`e142b26`) só como referência.
